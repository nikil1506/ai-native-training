Become an AI-native developer

No AI experience needed. Step by step, learn to build software with a coding agent, then to build your own agents and a small multi-agent system, checking your work with specs, tests and evals along the way.

Overview

A hands-on programme for developers who are new to AI. You do not need to have used a coding assistant or an LLM API. About a third of each day is concepts and a live guided walkthrough; the rest is lab work you do yourself, on scaffolded starter code, with facilitators on hand.

What participants will be able to do

  • Use a coding agent to deliver a feature and check its work — using a spec, tests and an independent review rather than trust.
  • Build a single-agent application, then a small multi-agent system, and show it works with an evaluation, a trace and a cost report.
  • Recognise when an agent is the wrong tool, and keep a human in charge of decisions and exceptions.
  • Apply the security basics for agents: limited permissions, prompt-injection defences, audit logs, approval steps.

How the course is organised

  • Foundations (Days 1–2): how models and agents behave.
  • Track A — Building with agents (Days 3–5): spec-driven development, independent review, the agent-assisted SDLC.
  • Track B — Building agentic systems (Days 6–12): tools, single agents, RAG, evals, observability, multi-agent design and orchestration.
  • Security and governance (Day 13).
  • Capstone (Days 14–15), assessed.

Design principles. Start simple and add one idea at a time. Teach patterns, not one tool's buttons. Make checking the agent's work the central skill. Everyone works individually, and everyone gets the same support: guided starts, hint cards and facilitators.

Pre-work and how you will be supported

About three hours before Day 1. It gets your tools working so that Day 1 can be about learning.

  • Setup clinic (1 h, live, the day before Day 1): install Git, Python 3.11+, an editor and your coding agent, and set up your API key. A facilitator helps until it works.
  • Complete the 20-minute diagnostic: a self-rating plus three short practical questions. It tells us where to give extra help; it does not affect your result.
  • Read the 10-page primer: plain-language LLM basics, the glossary in this guide, and the rules on acceptable use and data handling.
  • Run the setup check (make doctor). It confirms your key works and the starter repositories build.
  • You should be comfortable reading and writing basic code in one language. The course uses Python.

How you will be supported

Guided → your turn → stretch

Each lab starts with a facilitator walkthrough. You then do the tasks yourself, and the stretch task is optional.

Starter code with TODO markers

From Day 2 you complete working scaffolds rather than starting from a blank file. The scaffolds shrink as the course goes on.

Hint cards

Every lab has hints. Use them early; the point is to learn, not to struggle.

The stuck ladder

1. Re-read the task and the hint card (5 min). 2. Ask your coding assistant to explain the error, not to fix it. 3. Check the day's cheat sheet. 4. Ask a facilitator. 5. Skip to the next task, mark it, and catch up in office hours.

Explain it back

At the daily debrief you explain one thing you built in your own words. If you can explain it, you have learned it.

Reference solutions

The facilitator shares each reference solution after the lab so you can compare approaches.

Lab assignments

Every lab is done on your own and has an objective, starter code, a guided start, tasks, hint cards, deliverables and acceptance criteria. Tick the criteria as you meet them; progress is saved in your browser.

L1Your first API call: structured output and model trade-offsFoundationsDay 1 · 3 h

Objective. Make your first LLM API call, get answers in a fixed format, and measure accuracy, speed and cost on two models.

Starter. starter/l1 — 20 labelled support tickets (tickets.jsonl), a script with TODO markers, and a scoring helper.

Guided start. The facilitator makes the first API call live, prints the token usage, and shows where the key is loaded from.

Tasks
  1. Fill in the first TODO: make a chat call and print the reply, the token usage and the time taken.
  2. Run the same prompt 10 times at temperature 0 and at 1. Write three sentences on what changed and why.
  3. Make the classifier return {category, urgency, summary} using the structured-output option, then check it with the provided validator. Retry once if the output is invalid.
  4. Improve the prompt: clearer instructions, delimiters, three examples. Score each version with the helper.
  5. Run your best prompt on two model sizes and fill in the comparison table: accuracy, speed, cost per 1,000 tickets.
Hint cards
  • If validation fails, print the raw model output first and compare it with the schema.
  • Score with the helper script; do not judge by eye.
  • Cost per 1,000 tickets = tokens per ticket × 1,000 × price per token. The helper prints the first part.
Deliverables
  • Your script and scoring output
  • results.md with the comparison table and three sentences of conclusions
  • At least two prompt versions in git history
Acceptance criteria (tick as you go; saved in this browser)
Stretch
  • Add a ticket that says "ignore previous instructions" and see what the classifier does.
Common pitfalls
  • Judging quality by eye instead of scoring
  • Not noting which model version you used
  • Putting your API key in the code
L2Fix three bugs with a coding agentFoundationsDay 2 · 1.5 h

Objective. Learn to steer a coding agent and to review its work instead of accepting it blindly.

Starter. starter/bugfix-repo — a small service with three bugs (easy, medium, tricky) and failing tests.

Guided start. The facilitator fixes a demo bug live: asks the agent to explain the failing test, uses plan mode, reviews the diff, runs the tests.

Tasks
  1. Install and configure your coding agent. Read how its permissions work before you start.
  2. For each bug: write down your prompt, let the agent try, and read the diff before you accept it.
  3. For one bug, first ask the agent to investigate in read-only or plan mode, then approve the plan.
  4. Keep a steering log: what you asked, what the agent got wrong, how you corrected it.
  5. Run all the tests after each fix.
Hint cards
  • Ask the agent to explain the failing test before asking it to fix anything.
  • If the diff touches files you did not expect, reject it and make the prompt narrower.
  • Paste the exact test failure; it works better than describing it.
Deliverables
  • Fixed repository
  • steering-log.md
Acceptance criteria (tick as you go; saved in this browser)
Stretch
  • Write a rules file with three project conventions, then redo bug 3 and compare.
Common pitfalls
  • Accepting a big diff without reading it
  • Not running the tests
  • Starting over instead of correcting precisely
L3Build an agent loop from a templateFoundationsDay 2 · 1.5 h

Objective. Understand that an agent is a loop by completing a small one yourself.

Starter. starter/l3 — agent.py with TODO markers, five task prompts (one impossible), and a sandbox folder.

Guided start. The facilitator draws the loop on the whiteboard, then fills in the first TODO live.

Tasks
  1. Complete the loop: send messages and tool definitions, run any tool calls the model returns, add the results, stop when the model gives a final answer.
  2. Finish the two tools: calculator and read_file (only inside the sandbox folder).
  3. Add a maximum step limit and print each step with its token count.
  4. Send tool errors back to the model as messages instead of crashing.
  5. Run the five tasks and read the logs.
Hint cards
  • The loop: call the model → if it asked for tools, run them and add the results → repeat; otherwise stop.
  • A tool error is just another message to the model.
  • Resolve the file path and check it starts with the sandbox folder before reading.
Deliverables
  • Completed agent.py
  • Run logs for the five tasks
Acceptance criteria (tick as you go; saved in this browser)
Stretch
  • Allow several tool calls in one turn.
Common pitfalls
  • A loop with no limit
  • Letting the context grow without bound
  • Trusting file paths the model gives you
L4From a vague request to a working featureTrack A · Building with agentsDay 3 · 3 h

Objective. Practise the spec → tests → plan → build workflow with an agent.

Starter. starter/orders-app — a small web app and API with tests, a spec template, and a deliberately vague one-paragraph feature request.

Guided start. The facilitator shows how to ask the agent for ambiguities and compares a vague criterion with a testable one.

Tasks
  1. Ask the agent to list what is unclear in the request. Resolve at least four and write them down as assumptions.
  2. Fill in the spec template: problem, scope, what is out of scope, requirements, and acceptance criteria that a test can check.
  3. Write the acceptance tests before any implementation. The agent can help, but you read every test.
  4. Write a plan with at most five small tasks.
  5. Build one task at a time with the agent and commit after each.
  6. Note in deviations.md anywhere you ended up differing from the spec, and why.
Hint cards
  • A good criterion reads: given X, when Y, then Z.
  • If you cannot write a test for it, the criterion is too vague.
  • Keep each task small enough to review the diff in five minutes.
Deliverables
  • spec.md, plan.md, deviations.md
  • Acceptance tests
  • One commit per task
Acceptance criteria (tick as you go; saved in this browser)
Stretch
  • On another branch, ask the agent to "just build it" from the raw request and compare the bugs.
Common pitfalls
  • Vague words like "fast" or "easy to use"
  • Tests that just copy what the code does
  • Tasks too big to review
L5An independent reviewer and a reusable skillTrack A · Building with agentsDay 4 · 3 h

Objective. Build a reviewer that does not see the writer's thinking, deal with its findings, and package it so it can be reused.

Starter. Your L4 code, a findings template, and starter/sample-repo-2 for the reuse test.

Guided start. The facilitator builds a minimal review skill live and shows how a fresh context behaves differently from the writing session.

Tasks
  1. Create a reusable review skill, command or subagent for your tool. It starts with a fresh context and reports findings in a fixed format: ID, severity, file and line, issue, fix.
  2. Run it on your L4 code.
  3. Go through each finding in findings.md: accept it, dismiss it with a reason, or escalate it.
  4. Give the accepted findings to the writer agent, then run the reviewer again. Note what changed between round one and round two.
  5. Add a simple hook or script that stops a commit if the tests fail.
  6. Prove it is reusable: write a short README, then install and run the skill in sample-repo-2 using only your README.
Hint cards
  • Start the reviewer in a new session so it cannot see the earlier chat.
  • Ask it to look for problems, not to confirm things are fine.
  • If a finding is wrong, say so in findings.md and why; that counts as a good result.
Deliverables
  • Skill folder with README
  • findings.md with your decisions
  • Hook or script
  • Notes on rounds one and two
Acceptance criteria (tick as you go; saved in this browser)
Stretch
  • Use a different model for the reviewer and note whether it finds different problems.
Common pitfalls
  • A reviewer that only praises
  • Showing the reviewer the writer's reasoning
  • A hook so noisy you switch it off
L6A backlog item to a pull request, gate by gateTrack A · Building with agentsDay 5 · 2 h

L7Design tools for an agent, and wrap them in MCPTrack B · Building agentic systemsDay 6 · 3 h

Objective. Design a small set of tools an agent can use well, and see how much the descriptions matter.

Starter. starter/orders-api — a mock REST API with six endpoints (one destructive), an MCP server template, and eight task prompts.

Guided start. The facilitator turns one endpoint into a tool live and shows how a good description changes the agent's choice.

Tasks

  2. Implement them as function-calling tools, then expose them with the MCP server template.
  3. Connect an agent and run the eight task prompts.
  4. Make the descriptions worse on purpose (vague names, overlapping tools), run again, and note the difference.

Hint cards

L9Give the agent knowledge: RAG with citationsTrack B · Building agentic systemsDay 8 · 3 h

Objective. Let the agent answer from documents, show its sources, and measure how well retrieval works.

Starter. starter/policy-corpus — about 30 documents, 20 questions with the right source, 4 unanswerable questions, audience tags, and ingest and scoring helpers.

Guided start. The facilitator indexes the documents live and shows one question that retrieves the wrong chunk.

Tasks
  1. Run the ingest helper to chunk, embed and index the documents.
  2. Give the agent a retrieval tool that returns chunks with their source IDs.
  3. Make answers cite sources. For unanswerable questions the agent says it does not know.
  4. Measure how often the right document is in the top 5 (hit@5) with two chunk sizes, using the scoring helper.
  5. Use the filter helper so restricted documents are never returned to the wrong role.
Hint cards

  • Check each citation actually appears in what was retrieved.
  • Write the access test first: ask as the wrong role and expect nothing back.
Deliverables

L10Build an evaluation and improve by evidenceTrack B · Building agentic systemsDay 9 · 3 h

Objective. Create a repeatable test for your agent and use it to decide what to improve.

Starter. starter/eval — 12 ready-made test cases, a runner, a judge prompt template, and a score report.

Guided start. The facilitator runs the eval on a deliberately weak agent, reads two failures, and explains the score.

Tasks
  1. Add 8 of your own cases to the 12 provided (at least 3 awkward ones and 3 adversarial ones). Set 5 aside as a held-out group.
  2. Write two code checks (for example: the right tool was called, refunds escalated) and use the provided judge for answer quality.
  3. Check the judge: label 6 answers yourself and compare. Note where it disagrees and adjust the judge prompt.
  4. Run the baseline, make two improvements that each fix a specific failure, then run again and compare scores, including the held-out group.
  5. Add a small script that fails if the score drops below a threshold.
Hint cards
  • Write what you expect the agent to do before you run it.
  • Fix one failure at a time and re-run.
  • If the held-out score is far lower than the rest, you have over-fitted.
Deliverables
  • Your eval/ folder
  • Baseline and after reports
  • Threshold script
Acceptance criteria (tick as you go; saved in this browser)

Capstone

Each participant builds and presents a small multi-agent system on their own. You are not starting from nothing: the capstone extends your own L8–L13 work to a new scenario, using a scaffold repository that already has an orchestrator skeleton.

Scenario options

Support resolution assistant

Bug-report triage assistant

Document compliance checker

Glossary

Plain-language definitions of the terms you will meet. Keep this open during the first week.

Token
A small piece of text (part of a word) that a model reads and writes. Cost and limits are counted in tokens.
Context window
The amount of text a model can consider at once: your instructions, the conversation, and any documents.
Prompt
The instructions and information you give a model.
Temperature
A setting that controls how much a model's answers vary. Low is steadier; high is more varied.
Hallucination
When a model states something that sounds right but is wrong or made up.
Structured output
Asking the model to answer in a fixed format, such as JSON, so code can use the result.
Tool / function calling
Letting a model ask your code to do something, like look up an order, and use the result.
Agent
A model running in a loop: it decides what to do, uses tools, looks at the result, and repeats until done.
Coding agent
An agent that reads and edits your code and runs commands, for example to fix a bug.
Spec
A written description of what to build, including how you will know it works.
Acceptance criterion
A statement a test can check to confirm a feature works.
Independent reviewer
A second agent with a fresh context that checks the first one's work.
Finding
A problem a reviewer reports, with severity, location and a suggested fix.
Skill / hook
A reusable instruction set for an agent (skill), and an automatic check that runs at a set point, such as before a commit (hook).
MCP
Model Context Protocol: a standard way to offer tools and data to agents.
RAG
Retrieval-augmented generation: find relevant documents first, then let the model answer using them.
Embedding
A list of numbers that represents the meaning of text, used to find similar text.
Eval
A repeatable test that scores how well an agent does on a set of cases.
LLM judge
A model used to grade another model's answers against a rubric.
Guardrail
A limit or check that stops an agent from doing something unsafe or wasteful.
Prompt injection
An attack where text in a document or message tricks the model into following the attacker's instructions.
Multi-agent system
Several agents with different roles working together, often with an orchestrator.
Orchestrator
The part that decides which agent does what, and passes results between them.
Hand-off
The message one agent passes to another.
Trace
A record of every model call and tool call in a run, used to find out what happened.
Idempotent
Safe to repeat: doing it twice has the same effect as doing it once.

Instructor guide

What to prepare before the first cohort, and what can go wrong.

Preparation checklist

  • Choose Python for the whole cohort and prepare every starter repository in Python: bugfix-repo, orders-app, orders-api, support-agent, policy-corpus, eval, incidents, vulnerable-agent, sample-repo-2, backlog, and the capstone scaffold.
  • Starter code must run on first try. Dry-run every lab as a beginner would, on a fresh machine, and fix every TODO that is unclear.
  • Write a hint card and a one-page cheat sheet for every day, a worktree cheat sheet (L6), a review checklist (A1) and a trace-reading guide (A2).
  • Record the guided walkthroughs so a participant who falls behind can replay them.
  • Create the shared API gateway with a per-participant spending cap and a usage dashboard. Pilot Days 6–13 to calibrate the cap.
  • Default every lab to a smaller, cheaper model; use the stronger model only where a lab compares sizes.
  • Prepare reference solutions and grading sheets with the acceptance criteria. Pre-build the flawed PR (A1) and the three traces (A2), and have a second facilitator confirm the planted problems can be found.
  • Agree acceptable-use and data rules: no real customer data, no secrets in prompts, no production credentials.
  • Staff at one facilitator per six participants, plus one person on environment support on Days 1–2 and Day 6.

Measuring success

  • Self-assessment before and after: every participant rates themselves at least "can do with support" on each outcome.
  • At least 80% of participants pass A1, A2 and the capstone.
  • 30/60/90-day follow-up: each participant ships at least one agent-assisted change with a spec, review findings and a decision record, and adds one reusable skill or tool to a shared library.
  • Where measurable: cycle time, rework and escaped defects on agent-assisted work compared with a baseline.
