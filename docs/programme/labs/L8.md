**L8** A support agent with limits that are enforced*[Track B · Building agentic systems]*  (Day 7 · 3 h)

**Objective.** Build a single agent whose limits are enforced in code, and see how it behaves when things go wrong.

**Starter.** `starter/support-agent` — agent skeleton with `TODO` markers, your L7 tools, 15 support scenarios, and a failure-injection switch.

**Guided start.** The facilitator shows where a limit belongs in code, and why putting it only in the prompt is not enough.

##### Tasks

1. Complete the agent with `lookup_order`, `search_kb` (stub), `create_ticket` and `escalate_to_human`.
2. Enforce three limits in code: a step limit, a token budget, and the rule that refunds always go to a human.
3. Make the agent write its plan before it acts, and log it.
4. Turn on the failure-injection switch (tools sometimes fail or return bad data) and fix what breaks.
5. When an order number is missing, make the agent ask a question instead of guessing.

##### Hint cards

- Check limits inside the loop, before each model call.
- Treat a refund request as a hand-off, not a tool call.
- When a tool fails twice, escalate rather than retrying forever.

##### Deliverables

- Agent code
- `guardrails.md`
- Failure-injection run report

##### Acceptance criteria (tick as you go; saved in this browser)

- [ ] No run goes past the step or token limit in 10 runs
- [ ] No refund is ever carried out without escalation
- [ ] Every injected failure ends in a recovery or an escalation
- [ ] Missing order numbers lead to a question

##### Stretch

- Summarise the conversation after a few turns without losing key facts.

##### Common pitfalls

- Limits that exist only in the prompt
- Retrying forever
- Silent failures
